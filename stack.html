Three roads · Week 4 · Choose your stack with AI

How I decided what to build this with

I gave AI my four constraints, made it lay out three options from simplest to most powerful, pressure-tested the front-runner, and picked one myself. Then I built it — so the last section is what the decision actually cost me, measured rather than guessed.

00

The four constraints I gave it

1 · Budget

Free only. No hosting bill, no paid API tier, no domain purchase yet. I'm a student in Karachi funding my own degree — a recurring cost would kill the project.

2 · Honest skill level

Comfortable with Python, HTML, CSS, JavaScript, PHP, Flutter, FastAPI, Laravel. I have never shipped a React or Next.js app, and I'd be learning the framework and the content at the same time. Git and the command line are fine.

3 · What it must do

One-page argument with 8 ordered sections, 6 projects, 17 verifiable certifications, and a personal agent that answers questions about me. Full sitemap and content map: the through-line.

4 · How the work must show

Interactive 3D (the hero and the agent are the portfolio), outbound verification links for credentials, screenshots for projects later, and short reading — not long-form blogging.

Dynamic yet?

No. Nothing needs a database, logins, or server-side rendering. The agent answers from a knowledge base I write by hand. Deliberately answered before choosing, so I wouldn't buy a backend I don't need.

01

Three roads, simplest to most powerful

Road A · simplest

Hand-built static site + Three.js, on GitHub Pages

Chosen
How I'd buildPlain HTML, CSS and vanilla JS. Three.js as an ES module through an import map. No framework, no bundler, no npm install, no build step. Four hand-written pages.
Free hostGitHub Pages, straight off the main branch. Deploy = git push.
Backend?None. The agent is keyword-and-phrase retrieval over a knowledge base in a JS file.
Real trade-offNo components, so shared markup — nav, footer, head — is duplicated in every page and must be edited four times. No CMS: a new case study means copying an HTML file. That is the price, and it is paid in my time, not in money or in a broken deploy.
Road B · middle

Astro (or Next.js static export) + Netlify or Vercel

Not chosen
How I'd buildComponents for nav and footer, Markdown files for case studies, a layout system, `npm run build` to static HTML. Three.js still runs client-side.
Free hostNetlify, Vercel or Cloudflare Pages free tier, with preview deploys per branch.
Backend?Still none, but serverless functions are one file away if I ever need them.
Real trade-offA toolchain I've never run becomes a dependency of my portfolio being online. Node version mismatches, a broken lockfile or an Astro major version can take the site down at exactly the wrong moment, and I'd be debugging a build system instead of writing content. Real benefit — no duplicated nav — but bought with a risk I can't yet diagnose quickly.
Road C · most powerful

Next.js + serverless API routes + a real LLM + Postgres

Not chosen
How I'd buildReact components, API routes proxying an LLM so the agent answers anything, Neon Postgres for a contact form and analytics, maybe auth for a private area.
Free hostVercel hobby tier plus Neon free tier — free at my traffic, but both have quotas and both can suspend.
Backend?Yes, unavoidably. An API key cannot sit in client code, so a proxy is mandatory.
Real trade-offEvery extra part is a thing that can break while I'm asleep, and an LLM-backed agent can hallucinate about me — the exact failure my claim says I avoid. It also introduces a cost cliff: free until someone spams the endpoint. I'd be maintaining infrastructure to gain answers I can already write by hand.
02

Pressure-testing the front-runner

What breaks if I pick the simplest?

Repetition breaks first. Shared markup lives in four files, so a nav change is four edits and one of them will eventually be forgotten. Second, there's no image pipeline — I have to resize and compress screenshots myself. Neither of those takes the site down; both cost me minutes. Nothing in Road A can make the URL stop working, which is the failure I actually fear.

What do I maintain if I pick the most powerful?

A Node version, a dependency tree with security advisories, a build that must keep passing, an API key with a spend limit, a database that sleeps on the free tier, and a rate limiter so one bored visitor can't drain the quota. That's a system, and I'd be its only on-call engineer during exam weeks.

Can I finish in two weeks?

Road A: yes — I already know every language involved, so time goes into content and design. Road B: probably, minus a few days lost to learning the toolchain. Road C: no. I'd spend the two weeks on plumbing and ship a thin site with an impressive architecture and nothing in it.

Does it show my work the way it needs to be shown?

This was the deciding question. My work is interactive 3D and a live agent — both run in the browser, so a static host serves them perfectly. Certifications need outbound links, which cost nothing. Project screenshots need <img> tags. Nothing I must display requires a server. If my portfolio were a photo gallery or a blog with 50 posts, my answer would be Road B.

03

My decision, in my own words

I chose Road A: a hand-built static site with Three.js, hosted free on GitHub Pages.

I picked it because the thing I'm proudest of — a 3D companion that answers questions about me without an API key — is a browser thing, not a server thing. Adding a backend would not have made it better; it would have added something to break and a key to leak.

Can I maintain this? Yes, and that is the honest reason I chose it over Astro. There is no dependency to update, no build to fail, no Node version to match. If I don't touch this site for six months it will still be online, and when I come back the only skill I need is HTML. I've watched classmates lose projects to a broken build they couldn't debug, and I did not want my own portfolio to be that fragile.

Does it show my work well? Yes — better than Road C would have. The 3D scene and the agent both run client-side, so a static host is not a compromise for them, it's the natural home. The one thing it can't do is generate answers beyond my knowledge base, and that limit is the point: my agent says "I don't have that" instead of inventing something, which is exactly what my one-line claim promises.

Why not Road B: it solves a problem I don't have yet. I have four pages. When I have twelve and I'm copy-pasting a nav for the fifth time, Astro becomes the right answer — and because my site is plain HTML and CSS, migrating into it will be easy. Why not Road C: it trades my time for capability I don't need, and it would make my agent less trustworthy, not more.

Do I need a backend? Not yet. The trigger that would change my mind: needing per-user data, or a contact form that stores submissions, or an agent that answers beyond what I wrote. None of those is true today, so buying a backend now would be paying maintenance for a feature I don't have.

04

What the decision actually cost — after building it

The advantage of writing this after shipping: these aren't predictions.

OutcomeWhat happened
Held up Deploy speed 18 commits, every one live in roughly 30 seconds via git push. No build ever failed, because there is no build.
Held up No keys, no bills The agent runs entirely client-side. Nothing to rotate, nothing to rate-limit, nothing to pay. Total hosting cost to date: zero.
Held up 3D was free to add Three.js loaded as an ES module through an import map — no bundler config, which on Road B would have been my first real fight.
Bit me The CDN Loading Three.js from unpkg cost ~1 MB on every visit and made the site slow on a Pakistani mobile connection. Fixed by vendoring the library into the repo — a five-minute fix precisely because there was no build step to fight.
Bit me Duplicated markup Exactly the predicted trade-off: the nav and head block are copied across four pages. Adding the identity-kit link meant editing several files. Annoying, never dangerous — and the honest reason Road B will win eventually.
Bit me No image pipeline I resized and compressed the screenshots myself with a Python script (3.1 MB → 1.0 MB). A framework would have done it automatically.

Net: the two things that bit me cost me minutes and were both fixable without touching infrastructure. Nothing on Road A ever risked the URL going down. That's the trade I'd make again.
