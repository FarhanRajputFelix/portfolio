KIDO — a learning platform that answers to the parent

Most children's apps optimise for screen time. KIDO optimises for learning outcomes and child safety, with eleven cooperating agents behind it and a consent gate in front of every social action. It is live, deployed and installable.

01

The problem

Two things are usually in tension in children's software. A platform can be personalised — which means collecting behavioural data and letting an AI act on it — or it can be safe, which usually means locking everything down until it is inert. Products tend to pick one and quietly compromise the other.

KIDO's premise is that the tension is a design problem, not a law: an AI system can be genuinely capable and aligned with what a parent has actually agreed to, provided consent is a gate in the code rather than a checkbox in a settings screen.

02

The agent engine — the part that isn't a chatbot wrapper

On each learning event the platform runs an autonomous reasoning loop following the ReAct pattern. Three things make it a system rather than a prompt:

Tool-calling

Agents read the database, call the model, update XP and level, and raise parent alerts. They take actions with consequences, not just produce text.

Planning

An orchestrator decides which of the eleven agents run for a given event, and they share a common context rather than each starting cold.

Reflection, and a floor under failure

A Contradiction-Detection agent catches conflicting signals between agents. A Fallback-Recovery agent guarantees a safe result when the AI fails. The model chain degrades deliberately — Groq (Llama-3.3) → Gemini → curated content banks — so a provider outage produces worse content, never a broken experience for a child.

Every run persists as an explainable agent trace. That was the design decision I would defend hardest: if an AI is going to tell a parent something about their child, the parent's right to ask why has to be answerable from stored evidence, not reconstructed after the fact.

03

Safety, as enforced code

ControlHow it actually works
Verifiable Parental Consent A child cannot add a friend or join a classroom until a parent explicitly approves it. The consent is the gate, not a notification after the fact.
Server-side authorisation guard A single getAccessibleChild() check on every child-scoped API. Cross-account access returns 403. One gate, one place to audit — rather than a permission check copy-pasted into thirty handlers.
Age-gated content Children only see age-appropriate material, including in the video library.
Data minimisation Only learning data is stored. No ads, no third-party trackers.
Auth JWT sessions, bcrypt-hashed passwords, role-based access across child / parent / teacher / admin.

The single-guard pattern is the one I would point at in an interview. The common failure in multi-role apps is not a missing check — it is thirty checks that drift apart until one of them is wrong.

04

What it does

AI tutor that explains step by step and never simply hands over the answer · AI-generated adaptive quizzes that scale to the child's level · word, story and maths games · an age-gated video library · XP, levels, streaks, badges and leaderboards · teacher classrooms with join codes, AI quiz generation and progress analytics · tailored dashboards for child, parent, teacher and admin.

05

What I cannot prove

Shipped is not the same as validated

No learning-outcome evidence. KIDO is built to improve learning outcomes. I have no study, no A/B test and no before/after data showing that it does. The architecture is a hypothesis about how to help children learn; it has not been tested against one.

No real users at scale. It is deployed and installable, with demo accounts. There is no user base, no retention curve and no uptime record to point at.

The agents are evaluated by inspection. The traces make each run explainable, but there is no benchmark scoring whether the eleven agents make good decisions — only that they made explicable ones.

Built with AI assistance. The repository's contributor list shows two: me and Claude. Saying so costs nothing and makes the rest of this page easier to trust.

06

A correction worth leaving visible

Until 7 August 2026 this site described KIDO as Flutter, FastAPI, PostgreSQL, Redis, Python and OpenAI APIs. That was wrong. The real stack is Next.js and TypeScript with Prisma, Neon Postgres, Groq and Gemini. The Flutter claim traced to a real early commit that was later reverted to keep only the Next.js project, and the rest was simply stale.

I found it by reading my own repository instead of trusting my own summary of it — the same lesson recorded as failure point 9 on the workflow page. A public repo makes a wrong stack claim trivially checkable, which is a good reason to keep the repo public and the claim accurate.
