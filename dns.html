DNS walkthrough · PF-04 · Week 5

How a name finds my site

Written before I need it. When farhan.flyrank.ai is provisioned at the end of the track, FlyRank Ops creates one DNS record and I do the other half in my host's settings. This page is the checklist I'll run that day — and an explanation of what's actually happening, aimed at a colleague who has never touched DNS.

If you read one thing

DNS is a phone book for the internet. A CNAME record is a forwarding entry in that book: it says "this name is an alias for that other name — go look that one up instead."

Mine will say farhan.flyrank.ai → farhanbashir.netlify.app. Nothing about my site changes. A custom domain is a pointer, not a migration.

01

The idea, without jargon

Computers on the internet find each other by number, not by name. My site actually lives at an address like 75.2.60.5. Nobody wants to remember that, so DNS — the Domain Name System — exists to translate the name a human types into the number a machine needs.

The useful mental model is a very large, very fast phone book, split into sections that different organisations look after. Nobody holds the whole book. You get passed along until you reach the section that has your entry.

02

What a CNAME record is, and what mine will hold

A DNS entry is called a record, and records come in types. Two matter here:

TypeMeansExample
A "This name is this numeric address." The final answer. example.com → 75.2.60.5
CNAME "This name is an alias for another name. Stop asking about me; go and look that one up instead." Short for Canonical Name. farhan.flyrank.ai → farhanbashir.netlify.app

Mine will be a CNAME, and here is exactly what it will hold:

Type:   CNAME
Name:   farhan                    (the subdomain label, inside the flyrank.ai zone)
Value:  farhanbashir.netlify.app. (my host's name — the trailing dot makes it absolute)
TTL:    3600                      (seconds — how long resolvers may cache the answer)

The value depends on which host answers for the domain, and I run two. My canonical host is Netlify, so the value is farhanbashir.netlify.app. If I attached the subdomain to my GitHub Pages copy instead, the value would be farhanrajputfelix.github.io — the user site, never the /portfolio path, because DNS knows nothing about paths. It maps names to addresses and stops there.

The value is my host's name, not my own site's URL and not an IP address. That distinction is the whole point of using a CNAME: Netlify serves from an anycast network and can change which machines answer at any time, and my record keeps working because it points at a name they keep current. If I hardcoded an A record with today's IP and they renumbered tomorrow, my site would go dark and I'd get no warning.

Note the trailing dot in farhanbashir.netlify.app. — it marks the name as absolute. Some DNS interfaces add it for you; some treat a missing dot as "relative to this zone" and would silently create farhanbashir.netlify.app.flyrank.ai, which resolves to nothing. Worth checking rather than assuming.

Why a subdomain and not a bare domain

A CNAME cannot live at the apex of a domain — that is, at flyrank.ai itself with no label in front. The rules require the apex to also hold records like SOA and NS that identify the zone, and a CNAME is not allowed to coexist with other records for the same name. Since I'm being given farhan.flyrank.ai — a name with a label in front — a CNAME is exactly the right tool and this restriction never bites me.

03

What happens between the typing and the page

Someone types farhan.flyrank.ai and presses enter. All of this happens in well under a second, usually more like 50 milliseconds:

  1. The browser checks its own memory

    It keeps a short-lived cache of names it looked up recently. If my address is in there, the journey ends immediately and none of the steps below run. This is why a DNS change can look "not working" for you and fine for everyone else.

  2. The operating system asks the resolver

    If the browser doesn't know, it asks the OS, which asks a recursive resolver — usually run by the person's internet provider, or a public one like 1.1.1.1. "Recursive" means it does the legwork of asking around and comes back with a final answer, rather than telling you to go ask someone else.

  3. The resolver asks a root nameserver

    If the resolver has nothing cached, it starts at the top. The root servers don't know about me, but they know who is responsible for .ai, and they say so.

  4. The .ai nameservers point at flyrank.ai

    The resolver asks the .ai registry's nameservers about farhan.flyrank.ai. They don't know either, but they know which authoritative nameservers hold the records for flyrank.ai. The resolver is walking down the name one label at a time, right to left.

  5. flyrank.ai's nameservers return my CNAME

    These are authoritative — the actual source of truth for the zone. This is where the record FlyRank Ops created lives. They answer: "farhan.flyrank.ai is an alias for farhanbashir.netlify.app."

    Note what they did not return: an IP address. The question isn't answered yet, it's been redirected.

  6. The resolver starts over on the new name

    It now looks up farhanbashir.netlify.app, walking the same path — root, then .app, then Netlify's nameservers — until it gets A records with real IP addresses. This second lookup is the cost of a CNAME, and it's why a chain of aliases pointing at aliases makes a site slower.

  7. The answer comes back and gets cached

    The resolver hands the IP to the OS, which hands it to the browser. Everyone along the way remembers it for as long as the TTL allows. A TTL of 3600 means "you may reuse this for an hour" — which is also the honest explanation of "propagation": nothing is being pushed anywhere, old cached answers are simply expiring at their own pace.

  8. The browser connects, and only then does HTTPS happen

    Now it opens a TCP connection to that IP and starts a TLS handshake, saying which name it asked for. The host presents a certificate for farhan.flyrank.ai; the browser checks it was issued by an authority it trusts and that it actually covers this name. If both hold, the padlock appears and the page loads.

    DNS and HTTPS are separate steps. DNS finds the right building; the certificate proves the door has the right name on it.

04

Where the padlock comes from

I don't buy or install a certificate. Netlify requests one automatically from Let's Encrypt, free, using a protocol called ACME. GitHub Pages does the same for its copy.

The certificate authority has to verify I actually control the name before it will certify it, so it issues a challenge: it asks the host to serve a specific value at a specific path under farhan.flyrank.ai, then fetches that URL itself. Only someone who controls where the name points can pass, which is why the certificate cannot be requested until the CNAME resolves.

One detail specific to my host: .app is on the HSTS preload list, which means browsers refuse to load any .app address over plain HTTP before a request is even sent. So farhanbashir.netlify.app could never have been served insecurely, whatever I configured.

Hence the correct order, and the reason the padlock is often missing for a few minutes: record first, then domain added at the host, then certificate. A certificate error right after setup usually means the challenge ran before DNS had settled, and the fix is to wait and retry rather than to change anything.

05

The checklist I'll run on the day

Ops creates the record. My half is everything below.

  • Confirm with Ops that the CNAME exists and note the exact value they used
  • Verify it resolves from my machine: nslookup farhan.flyrank.ai — I expect to see the alias, then GitHub's addresses. If it returns nothing, stop and wait; don't start changing settings
  • Add farhan.flyrank.ai in Netlify: Site configuration → Domain management → Add a domain. Netlify will detect the CNAME already exists and verify it
  • Update the rel="canonical" tag on all 14 pages and the URLs in sitemap.xml to the new host, then re-run tools/check-links.py — otherwise every page still tells search engines the Netlify name is the real one
  • Wait for the certificate. Tick "Enforce HTTPS" once it's available, not before
  • Open https://farhan.flyrank.ai in a private window while logged out, and check the padlock and the certificate's name
  • Click through every page from the homepage — a custom domain shouldn't change relative links, but my link checker takes seconds to run and I once shipped six unreachable pages
  • Confirm the old URL still works. Both keep working; the new name is an addition, not a move
  • Update the link on LinkedIn and in my CV
The three mistakes I expect to be tempted by

Panicking during the TTL. An old cached answer isn't a broken record. If nslookup against 1.1.1.1 gives the right answer and my browser doesn't, the record is fine and I'm impatient.

Forcing HTTPS too early. Enforcing it before the certificate is issued makes the site unreachable rather than merely unencrypted.

Pointing the CNAME at the wrong thing. The value is my host's name (farhanbashir.netlify.app), not https:// in front of it, not a path after it, and not an IP address I looked up today.
