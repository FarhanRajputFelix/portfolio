My pipeline is a workflow, not an agent

And the honest reason is that I wrote the order of the steps. Below: the distinction, where my FL-04 build sits, what MCP is, and the one upgrade that would move it across the line.

If you read one thing

My FL-04 pipeline is a workflow, not an agent — because I wrote the order of the steps. An agent decides its own. MCP is what turns those steps into callable tools so the model can choose.

The classification argument is §02. The one upgrade that crosses the line is §05.

01

Workflow or agent — who decides the next step?

Anthropic's Building Effective Agents draws the line in one place, and it isn't capability or cleverness. A workflow is a system where models and tools are orchestrated through predefined code paths. An agent is a system where the model dynamically directs its own process and tool usage, keeping control over how it reaches the goal. Both are "agentic systems"; the difference is who owns the control flow.

So the test is one question: at each step, does the sequence come from the author or the model? If I can draw the flowchart before the task starts, it's a workflow — however many steps, however smart each one. If the step count can't be known in advance because the model decides what comes next from what it just learned, that's an agent.

The essay is blunt about the trade: agents buy performance with latency and cost, so find the simplest thing that works — sometimes that means no agent at all. Handing over control is a cost, not a prize.

02

Classifying my FL-04 build

My Opportunity → outreach pack pipeline runs five steps: gather, evidence map, draft, adversarial audit in an isolated chat, format.

Verdict: a workflow — specifically prompt chaining with a gate.

Each step's output is the next step's input, in an order I fixed before any posting existed. The model never selects a step. I carry text between the five prompts by hand.

Two details look like agency and are not. First, step 2 can emit CALL: skip and stop the run — which killed the DAAD WISE application in 38 seconds. That is real decision-making, but it is a conditional inside a path I predefined: I decided in advance that a skip verdict halts the chain. A branch I wrote is still my branch.

Second, step 4 runs in a deliberately fresh chat so the auditor can't be persuaded by the reasoning that produced the draft — and that isolation is only achievable because I control the path. A model directing its own process would carry its context forward, which is exactly what the audit exists to prevent. Here, being a workflow is the feature.

03

What MCP is

The Model Context Protocol is an open standard for connecting AI applications to outside systems — the docs call it a USB-C port for AI applications. Before it, every integration was bespoke; now you build a server once and any compliant client can use it.

The shape is client–server. A host (Claude Desktop, Claude Code, VS Code) spawns one client per server, each holding a dedicated connection. Underneath it's JSON-RPC 2.0 over either stdio for local processes or streamable HTTP for remote ones. A server exposes three primitives, and what makes them distinct isn't format — it's who is in control:

PrimitiveControlled byWhat it's forIn my server
Tools the model Executable functions the model invokes to take action — API calls, file writes, queries. Discovered with tools/list, run with tools/call. fetch_posting, check_gpa_gate, log_run
Resources the application Data that provides context — file contents, records, API responses. The host decides what to attach; the model doesn't fetch them at will. both knowledge files and all 7 run transcripts, under outreach://
Prompts the user Reusable templates a human picks deliberately — the slash-command menu. my five pipeline steps, step1_gather … step5_pack

That control split is the part worth memorising. "MCP gives Claude tools" is the marketing summary and it misses two thirds of the protocol.

04

The server I built, and three things chat can't do

I wrote outreach-mcp — zero dependencies, stdio transport, raw JSON-RPC, all three primitives: mcp/. Full protocol transcript: evidence/transcript.txt.

1 · Fetch a live postingnetwork I/O

fetch_posting pulled https://sparai.org/ — HTTP 200, 358,124 bytes of HTML stripped to 12,931 characters, carrying the live deadline ("Apply by August 18") and "230+ mentors for Fall 2026". A chat window cannot open a socket; without this the posting gets pasted by hand.

2 · Answer a GPA gate without disclosing the GPAprivate local file

check_gpa_gate reads pipeline/private/cv-private.md — gitignored, never published. Against KAUST VSRP's stated 3.5/4 minimum it returned VERDICT: FAIL → skip; against a 2.5/4 threshold, VERDICT: PASS.

Neither response contains the number. The tool returns the decision and keeps the CGPA on the machine — which is the whole argument for a tool over a paste. Pasting the file into a chat would disclose it permanently to get the same one-bit answer.

3 · Write state that outlives the conversationpersistence

log_run appends to pipeline/runs/INDEX.md, creating it on first call. Running the client twice appended row 1, then row 2 — state surviving across separate processes, which conversation history cannot do.

Two implementation notes. The current spec revision (2026-07-28) is stateless and discovers via server/discover, while most shipping clients still send the older initialize — my server answers both. And because a resource URI is model-supplied input, every read is canonicalised and rejected if it escapes the project root.

05

The one upgrade that would make it an agent

Replace my hand-carried five-step sequence with a single loop that has a stop condition, and let the model choose which tool to call next.

Concretely: one prompt stating the goal — produce a send-ready outreach pack, or a justified skip — the three tools, the knowledge files as resources, and a loop that keeps returning tool results to the model until it emits the pack. Nobody writes the order. Given a posting with a GPA minimum, the model calls fetch_posting, notices the threshold, calls check_gpa_gate unprompted, gets FAIL, logs a skip and stops — three calls I never sequenced. Given a posting with no GPA gate it never makes that call at all. The step count stops being knowable in advance, which is precisely the line from §01.

The MCP server is the prerequisite: that loop is only possible once the steps exist as callable capabilities rather than prompts I copy between windows. And I'd pay for it — the audit's isolation is a property of the path, so an agent managing its own context would need that enforced as a tool boundary instead. Worth doing at twenty postings a week. At five, the workflow is still the right call.
