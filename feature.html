Make it do something · Week 8

One feature: a contact form that actually arrives

The brief asked for exactly one dynamic feature, working end to end on a free tier. This is it — the form in the contact section. Two test submissions are in my inbox, and the interesting part turned out to be that the HTML was correct for an hour while the feature was completely dead.

If you read one thing

I did not build a backend. I added one HTML attribute — data-netlify="true" — and rented Netlify's.

The form returned 404 for an hour with byte-identical markup, until I enabled a setting. That is the whole lesson: the backend was never in my code.

01

What a backend is, in plain words

A backend is server-side code that runs after a form is submitted — it receives the data, validates it, stores it somewhere, and decides what happens next (save to a database, send an email, and so on). A plain HTML file can't do any of that, because HTML only describes the structure and content of a page. A description can't execute.

So without a backend, clicking "Send" has nowhere to go. To be precise about it: there is a server on the other end — Netlify's, and it answered every request I made. What it lacked was any code registered to run when a submission arrived at that address. That is exactly why my test got a 404 rather than a connection error: the server was reachable, it just had nothing to hand the data to.

What my feature actually does

My "feature" doesn't have a backend I built. I didn't write a server, a database, or an email service. What I did was add data-netlify="true" to the form tag, plus a matching name attribute. That one attribute tells Netlify's own infrastructure to treat my form as theirs to handle — so I'm effectively borrowing Netlify's backend instead of running my own.

How the data flows

  1. A visitor types into the fields and hits Send.
  2. The browser does a normal POST to my own page's URL. No JavaScript of mine is involved.
  3. Netlify's servers intercept that POST and recognise it by the form's name.
  4. They check the hidden honeypot field to filter out bots — a real person never sees it, so anything with it filled in gets dropped.
  5. If it's clean, they store the submission and fire an email to me.
  6. The browser is redirected to /thanks.html.

The detail that taught me the most

The form was returning a 404 until I flipped a setting in Netlify — even though the HTML markup itself never changed between the failing and the working version. That's the tell that the "backend" isn't anything living in my code at all. It's an external service that has to be explicitly told "this form exists, please watch for it". Until you flip that switch, Netlify has no idea your form is there, no matter how correct your HTML is.

02

Evidence it works

Four POSTs to the live endpoint. The third one is the reason this counts as proof rather than a hopeful guess — a negative control, to show a 200 means "this specific form is registered" and not "the server says 200 to everything".

TestResultWhat it establishes
Before enabling detection 404 The markup alone does nothing. The feature was inert.
form-name=contact 200 Registered and accepting. Two emails arrived in my inbox.
form-name=does-not-exist 404 Negative control. The 200 above is specific to my form, not a blanket response.
Honeypot field filled 200, not delivered Accepted at the edge and discarded as spam, so bots get no signal that they were filtered.
Two honest limits

The form only works on this host. My site is also served from GitHub Pages, where the same markup renders and does nothing, because Pages serves files and runs no code. Same HTML, no backend behind it — the same lesson as the 404, from a different direction.

The free tier caps at 100 submissions a month. Beyond that, submissions stop rather than queue. Fine for a portfolio; worth knowing it's a ceiling and not a soft limit.

03

Choices in the build worth naming

ChoiceWhy
No JavaScript The browser's native form POST does the work, so the feature survives a JS error, a blocked script or a slow connection. Everything else on my homepage degrades; this shouldn't.
Honeypot, not a captcha A captcha makes every human do work to stop some bots. A honeypot makes bots identify themselves and costs humans nothing.
Hidden with clip-path, not display:none Some bots skip display:none inputs, which defeats the trap. It's also removed from the tab order so keyboard and screen-reader users never meet a field asking them to leave it empty.
Labels bound by id, native validation Real <label for> pairs, required, and type="email". :user-invalid means error styling appears only after a failed submit, not while someone is mid-typing.
A real success page /thanks.html confirms delivery and offers a next step, rather than Netlify's generic screen. It's noindex and unlinked, so my link checker needed an explicit exception rather than a loosened rule.
